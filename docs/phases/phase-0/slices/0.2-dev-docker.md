## Spec

### Mục tiêu

Chạy được mọi lệnh dev (`pnpm install`, `lint`, `typecheck`, `test`, `build`) qua Docker Compose. Host chỉ cần Docker và `make`, không cài Node hay pnpm.

### Trong phạm vi

- `compose.yaml` ở root với một service `dev` (Node 26 + pnpm qua Corepack)
- Dockerfile cho service `dev`
- `Makefile` bọc các lệnh hay dùng
- `node_modules` nằm trong repo qua bind mount, pnpm store nằm ở named volume
- File sinh ra trong container thuộc user của host, không thuộc root
- Hướng dẫn setup trong `README.md`, kể cả cách cấu hình Node interpreter cho WebStorm
- Cập nhật mục "Lệnh thường dùng" trong `CLAUDE.md`
- ADR-0002

### Ngoài phạm vi

- Service postgres, api, web và hot reload (slice 0.5)
- CI (slice 0.6)
- Dev Container (`.devcontainer/`)
- Image production

### Q1. Môi trường dev chạy trên host hay trong Docker?

- **Trạng thái:** ✅ Đã chốt (2026-10-21)
- **Bối cảnh:** máy dev (Ubuntu 26.04) chưa có Node, chưa có trình quản lý version. Docker 29.9 đã có, user nằm trong group `docker`.
- **Phương án:**
  - A: Hybrid. Node cài qua nvm trên host (theo Q6/Q7 của slice 0.1), Docker chỉ chạy runtime
  - B: `docker run node:26 ...` từng lệnh, không có compose
  - C: Dev Container
  - D: Service `dev` trong Docker Compose, gọi qua `make`
- **Quyết định:** D. Chi tiết ở ADR-0002.
- **Lý do:** host sạch, mọi máy dùng cùng một môi trường. Các service ở slice 0.5 và các stack của phase sau (Go, PHP) chạy cùng một cách. Đánh đổi chính (gõ lệnh dài, quyền file, IDE) đều xử lý được bằng Q4 và Q5.
- **Đã kiểm tra:** binary native (esbuild, SWC) không lệch nền tảng, vì host và image đều là Linux x64 glibc. IDE không cần Node trên host. VS Code dùng Node có sẵn của nó, WebStorm dùng interpreter trong Docker (Q9). Cả hai chỉ cần thấy `node_modules`.

### Q4. Gõ lệnh thế nào cho gọn?

- **Trạng thái:** ✅ Đã chốt (2026-10-21)
- **Phương án:**
  - A: `Makefile` (`make install`, `make lint`, ...)
  - B: script `./bin/pnpm` chuyển mọi tham số vào container
  - C: cả hai
- **Quyết định:** A. Thêm target `make pnpm ARGS="..."` cho lệnh không có sẵn target (ví dụ `make pnpm ARGS="add -D x --filter @crm/api"`) và `make sh` để mở shell trong container.
- **Lý do:** Ubuntu có sẵn `make`, các lệnh hay dùng ngắn gọn và tự làm tài liệu.

### Q5. `node_modules` và pnpm store nằm ở đâu?

- **Trạng thái:** ✅ Đã chốt (2026-10-21)
- **Phương án:**
  - A: `node_modules` trong repo (bind mount), pnpm store ở named volume
  - B: `node_modules` ở named volume
- **Quyết định:** A. Container chạy bằng UID/GID của host (xem Q7).
- **Lý do:** IDE trên host thấy package nên có gợi ý type và lint. Store ở volume giúp cài lại nhanh mà không làm bẩn repo.
- **Hệ quả:**
  - Store (volume) và `node_modules` (bind mount) khác filesystem, nên pnpm không hardlink được và sẽ copy file. Lần cài đầu chậm hơn, cần đo (xem Tiêu chí hoàn thành).
  - Named volume mới tạo thuộc root. Image phải tạo sẵn thư mục store với owner là UID 1000 để volume thừa hưởng quyền.

### Q6. Base image?

- **Trạng thái:** ✅ Đã chốt (2026-10-21)
- **Phương án:**
  - A: `node:26-trixie-slim` (Debian 13, glibc)
  - B: `node:26-alpine` (musl, nhẹ hơn)
  - C: `node:26` bản đầy đủ
- **Quyết định:** A.
- **Lý do:** glibc khớp với host nên binary native trong `node_modules` dùng được cho cả host lẫn container. Alpine dùng musl, dễ lỗi binary native. Bản đầy đủ nặng hơn mà không cần thêm gì.

### Q7. Truyền UID/GID của host vào container thế nào?

- **Trạng thái:** ✅ Đã chốt (2026-10-21)
- **Phương án:**
  - A: `user: "${UID:-1000}:${GID:-1000}"` trong `compose.yaml`, `Makefile` export `UID`/`GID` từ `id -u`/`id -g`
  - B: build image với user có UID trùng host (build arg)
  - C: chạy root rồi `chown` sau
- **Quyết định:** A.
- **Lý do:** không phải build lại image khi đổi máy. Máy hiện tại có UID/GID là 1000, trùng với user `node` trong image.
- **Hệ quả:** nếu UID khác 1000 thì user không có trong `/etc/passwd` của image và không có `HOME`. Đặt `HOME` cố định trong compose để pnpm và Corepack có chỗ ghi cache.

### Q8. Có giữ `.nvmrc` không?

- **Trạng thái:** ✅ Đã chốt (2026-10-21)
- **Phương án:**
  - A: giữ, làm nguồn duy nhất cho major version Node. `Makefile` đọc file này và truyền vào build arg của image
  - B: xoá, ghi version trực tiếp trong Dockerfile
- **Quyết định:** A.
- **Lý do:** CI ở slice 0.6 có thể dùng `actions/setup-node` đọc `.nvmrc`. Ai muốn cài Node trên host vẫn dùng được.

### Q9. WebStorm dùng Node interpreter nào?

- **Trạng thái:** ✅ Đã chốt (2026-10-21)
- **Phương án:**
  - A: interpreter dạng _Docker Compose_, trỏ vào service `dev`
  - B: không cấu hình Node, chỉ dùng TS service tích hợp
- **Quyết định:** A, ghi các bước vào `README.md`. PhpStorm có sẵn plugin Node.js, cấu hình giống WebStorm.
- **Lý do:** ESLint và TypeScript service của WebStorm cần Node để chạy. Thiếu Node thì không hiện lỗi lint inline.

### Q10. Cài pnpm trong image thế nào?

- **Trạng thái:** ✅ Đã chốt (2026-10-21)
- **Bối cảnh:** từ Node 25, Corepack không còn đi kèm Node (slice 0.1, Q6).
- **Phương án:**
  - A: `npm i -g corepack` + `corepack enable`. Copy `package.json` vào lúc build để `corepack install` tải sẵn đúng bản pnpm ghim trong `packageManager`, cache vào thư mục ai cũng đọc được (`COREPACK_HOME`)
  - B: như A nhưng không tải sẵn, Corepack tải pnpm lần đầu chạy lệnh
  - C: `npm i -g pnpm@<version>`, ghi version vào Dockerfile
- **Quyết định:** A.
- **Lý do:** vẫn chỉ có một nguồn version là `packageManager`, đúng tinh thần Q6 cũ. Không phụ thuộc mạng mỗi lần chạy container mới. Đổi version pnpm thì `package.json` đổi, cache layer bị huỷ và image tự build lại.

### Lệch so với plan

- **Một volume cho cả `HOME` (`dev-home`) thay vì volume riêng `pnpm-store`.** Store nằm ở `/home/dev/.pnpm-store`, cùng volume với các cache khác (Corepack, npm). Ít volume hơn, và `HOME` cũng cần ghi được khi UID khác 1000 (Q7).
- **Biến môi trường store là `pnpm_config_store_dir`.** pnpm 12 bỏ qua `npm_config_*`. Nếu không đặt rõ store-dir, vì store khác filesystem với repo, pnpm tự đặt store vào `node_modules/.pnpm-store`.
- **Image chạy `pnpm -v` lúc build.** pnpm 12 tải binary native (`pnpm-native`) vào thư mục cài của nó ở lần chạy đầu. Không làm lúc build thì mỗi container `--rm` lại tải lại.
- **Corepack ghim `0.36.0`.** Image `node:26` không có Corepack (đã kiểm tra), cài qua npm.
- **`.dockerignore` dạng whitelist** (chỉ `package.json`) thay vì liệt kê thư mục cần bỏ. Image không chứa source, nên build context chỉ cần file này.
- **`compose.yaml` có giá trị mặc định `NODE_VERSION=26`, `UID/GID=1000`** cho trường hợp gọi compose không qua `make` (ví dụ WebStorm). Giá trị `26` lặp lại `.nvmrc`, đổi Node thì phải sửa cả hai.
